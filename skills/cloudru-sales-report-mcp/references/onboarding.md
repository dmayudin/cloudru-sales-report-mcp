# Первые шаги пользователя

## Первое сообщение после установки

«Помогу получить отчёт по выручке и марже в облаке. Техническую настройку выполню сам. Сначала нужны три ответа:
1. У вас уже есть аккаунт Cloud.ru: да, нет или не уверены?
2. Откуда берём продажи: готовый файл, облачная папка или учётная система?
3. Отчёт нужен один раз или с обновлением? Если пока не решили — начнём с разового.
Ключи и пароли сюда не присылайте. Перед созданием ресурсов покажу стоимость.»

Не спрашивай повторно то, что уже известно. Предложи простой пример выгрузки только после ответа об источнике. Сначала проверь возможность безопасного подключения в данном агенте: skill installation не означает наличие облачного MCP.

## Если аккаунта нет

Показывай только ближайший выполнимый шаг, затем продолжай с достигнутого места. Не выдавай сразу список всех технических операций.

1. «Откройте [регистрацию Cloud.ru](https://console.cloud.ru) и выберите “Зарегистрироваться”. Доступен вход с регистрацией по телефону/email или Сбер ID. Завершите подтверждение самостоятельно; коды мне не нужны.»
2. «Если отчёт нужен организации, оформите аккаунт организации по подсказкам Cloud.ru. Договор и платёжные данные заполняете вы; я не прошу передавать их в чат.»
3. «Когда увидите личный кабинет, напишите “вошёл”. Далее подключим доступ только к проекту отчёта.»
4. Баланс/пополнение пользователь выполняет сам. Не предлагай произвольную сумму: сначала объясни минимальные необходимые расходы и предварительную оценку; после доступа уточни смету. Не обещай доступность бонусов или free tier до проверки.

Источник: [начало работы](https://cloud.ru/docs/evolution/overview/topics/getting-started), [оплата физическими лицами](https://cloud.ru/docs/billing/ug/topics/concepts__cycle_fl), проверены 28.10.2026. Названия экранов могут измениться: сверяй инструкции по официальной документации, без управления браузером пользователя.

## Если аккаунт уже есть

«Используем отдельный проект для отчёта или выбранный вами существующий. Если доступом управляет ваша организация, понадобятся права её администратора. Мне не нужен ваш личный пароль.»

Агент определяет проект через API после подключения. До подключения достаточно названия проекта; ID запрашивать только если безопасный механизм подключения требует его и не умеет выбрать проект. Тогда объяснить, где его скопировать, одним шагом. Не просить пользователя искать сети, образы, спецификации или роли БД.

## Первичный доступ Cloud.ru

Пользователь сам работает в своей консоли; запрет браузера относится к агенту, а не к регистрации пользователя.

Перед выдачей инструкции агент подготавливает точный набор прав по актуальным справочникам Cloud.ru для создания VM/сети/DNS/S3/ClickHouse/Data Platform/BI в выбранном проекте. Не выдумывай названия ролей и не предлагай администратора всей организации как универсальное решение. Если прав не хватает, назови конкретный отсутствующий доступ и его назначение.

1. «Откройте “Пользователи” → “Сервисные аккаунты” → “Создать аккаунт”. Назовите его “Отчёт по продажам”. Это отдельный доступ для программы, не новый пользователь вашей команды.»
2. «Выберите уровень “Проект” и проект отчёта. Назначьте перечисленные мной права только в этом проекте. Подтвердите создание.» Агент вставляет проверенный список прав, а не заставляет пользователя выбирать самостоятельно.
3. «Откройте созданный аккаунт. В блоке “Учётные данные доступа” выберите вкладку “Ключи доступа” → “Создать ключ”. Укажите название и срок, соответствующий согласованному использованию.» Не путать эту вкладку с “API-ключи”: текущий IAM-адаптер использует пару Key ID / Key Secret.
4. «Оставьте окно с ключом открытым: секрет показывается один раз. Сейчас дам защищённое место для ввода. Не вставляйте его в сообщение.»

Источники: [создание аккаунта](https://cloud.ru/docs/console_api/ug/topics/guides__service_accounts_create), [создание ключа доступа](https://cloud.ru/docs/console_api/ug/topics/guides__service_accounts_key-create), проверены 28.10.2026.

## Безопасный ввод

Предпочитай встроенный secret store/защищённую форму текущего агента или проверенного оператора MCP. Сообщи пользователю, куда именно передаётся ключ и кто получает доступ. Не называй обычный чат защищённой формой.

В этой поставке готов терминальный помощник credentials.py. Агент сам подготавливает команду и доверенный терминал, пользователю остаётся вставить значения в поля без эха. Объяснение: «Во время вставки символы не отображаются — это нормально. Вставьте идентификатор ключа, нажмите Enter, затем секрет и Enter. Значения не попадут в чат». Не читать clipboard или секретные файлы обратно ради проверки. Проверка — успешный read-only API-запрос.

Для первичного bootstrap, когда облачной VM ещё нет, используется защищённое окружение API-клиента агента/оператора, без запуска локального приложения. После создания VM агент переносит доступ в защищённое окружение облачного runtime. Не предлагай ввести ключ на несуществующем сервере. Если доступного безопасного механизма нет, сообщи это до создания ключа и не проси секрет в чат.

Доступ S3 и BI запрашивай только при достижении соответствующего шага. Все генерируемые системой пароли создаёт агент на исполнителе. Нужный вид BI API credentials сначала проверяется: нет подтверждённого универсального обмена Cloud.ru IAM → Superset JWT. Не отправляй человека искать несуществующую кнопку «получить BI токен».

После проверки: «Доступ подключён к проекту [название]. Дальше техническую настройку выполню сам. Сейчас проверю данные и покажу месячную стоимость».

## Данные и режим

- Разово: один файл → период/смысл показателей → срок доступности ссылки. Спросить «Как долго нужен доступ к отчёту?» Разовый импорт не означает разовый счёт: работающий BI продолжает тарифицироваться.
- Новые файлы вручную: пользователь присылает очередной полный снимок; агент обновляет существующий отчёт. Это обновление по запросу, не автоматический сбор.
- Автоматически: конкретный источник + разрешённый доступ + частота + часовой пояс. Сейчас реализован один приватный S3-объект `source/sales.csv` в бакете сценария. Подготовку доступа выполняет агент. Источник должен действительно доставлять туда новые данные.
- Google Drive/Dropbox/1С/Ozon/WB: сначала проверить наличие поддерживаемого коннектора и его права. Не выдавать предложение интеграции за уже работающий коннектор. До реализации предложить разовый файл или обновление по запросу.

Отсутствие новых данных показывать как «новых данных пока нет», сбой доступа — как «не удалось обновить, последний успешный отчёт сохранён». Не объявлять повтор старого файла свежими продажами.

Читайте [стоимость и управление](product.md). До расходов — полная оценка и согласие; после проверки — ссылка, способ входа, период, дата данных, режим обновления и месячная стоимость. Пользователь не получает Terraform state, ключи или технический перечень как основной результат.
