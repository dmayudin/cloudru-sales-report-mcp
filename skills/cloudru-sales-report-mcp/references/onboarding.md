# Первые шаги пользователя

## Первое сообщение после установки

«Помогу получить отчёт по выручке и марже в облаке Cloud.ru. Техническую настройку выполню сам; от вас понадобятся два коротких действия в консоли и ответы на три вопроса:
1. У вас уже есть аккаунт Cloud.ru: да, нет или не уверены?
2. Откуда берём продажи: готовый файл, облачная папка или учётная система?
3. Отчёт нужен один раз или с обновлением? Если пока не решили — начнём с разового.
Ключи и пароли сюда не присылайте: для них будет отдельное защищённое окно. Перед созданием ресурсов покажу стоимость.»

Не спрашивай повторно то, что уже известно. Предложи простой пример выгрузки только после ответа об источнике. Сначала проверь возможность безопасного ввода в данном агенте (вкладка терминала): установка навыка не означает наличие облачного MCP.

## Если аккаунта нет

Показывай только ближайший выполнимый шаг, затем продолжай с достигнутого места. Подробные карточки регистрации и выбора проекта — в [first-time-cloud.md](first-time-cloud.md) (разделы про сервисный аккаунт и роли там больше не нужны: это делает шаблон).

1. «Откройте [регистрацию Cloud.ru](https://console.cloud.ru) и выберите „Зарегистрироваться“. Доступен вход по телефону/email или Сбер ID. Коды подтверждения мне не нужны.»
2. «Если отчёт нужен организации, оформите аккаунт организации по подсказкам Cloud.ru. Договор и платёжные данные заполняете вы.»
3. «Когда увидите личный кабинет, напишите „вошёл“.»
4. Баланс/пополнение пользователь выполняет сам; агент заранее называет минимальные расходы на согласованный срок (см. product.md), не произвольную сумму. Free tier BI не обещать до проверки.

Источник: [начало работы](https://cloud.ru/docs/evolution/overview/topics/getting-started), [оплата физическими лицами](https://cloud.ru/docs/billing/ug/topics/concepts__cycle_fl), проверены 28.10.2026.

## Если аккаунт уже есть

«Работать будем в отдельном проекте для отчёта или в выбранном вами существующем. Если доступом управляет ваша организация, нужны права её администратора в этом проекте. Личный пароль мне не нужен.»

Проект агент определяет через API после подключения (подсказка из токена и список проектов). Не проси пользователя искать ID проекта, сети, образы, спецификации или роли.

## Доступ: два действия пользователя

Полный текст, скриншоты и запасные формулировки — в [console-steps.md](console-steps.md). Коротко:

1. **Личный ключ доступа** (шаг B): инициалы справа вверху → «Мой профиль» → «Ключи доступа» → «Создать ключ». Срок: 7 дней для разового отчёта, 30 дней для обновляемого. Key ID и Key Secret пользователь вставляет в защищённую вкладку терминала, которую агент открывает заранее (`scripts/connect_cloud.py`): «Символы при вставке не отображаются — это нормально. Вставьте Key ID, Enter, затем Key Secret, Enter. В чат ничего не попадёт». Проверка — успешный ответ IAM, затем read-only запросы.
2. **Tenant ID Object Storage** (шаг C): меню сервисов → «Хранение данных» → «Object Storage» → «Параметры работы с API». Это идентификатор, его можно прислать в чат.

Почему именно личный ключ: API Data Platform (Managed BI) не принимает сервисные аккаунты (500/403 при любых ролях, проверено 28.10.2026). Сервисный аккаунт для сервера агент создаёт сам через API вместе с ролями и ключом; пользователю его искать и настраивать не нужно. Если пользователь уже создал сервисный аккаунт по старой инструкции, его можно указать в deployment.json, но bootstrap всё равно ведётся личным ключом.

После проверки: «Доступ подключён к проекту [название]. Дальше техническую настройку выполню сам: проверю данные, соберу план и покажу стоимость одним сообщением».

## Безопасный ввод

Предпочитай встроенный secret store/защищённую форму текущего агента. Сообщи пользователю, куда передаётся ключ (только IAM Cloud.ru по HTTPS и файл 0600 на его машине до переноса на сервер). Не называй обычный чат защищённой формой. Не читай буфер обмена или секретные файлы обратно ради проверки. После переноса секретов на VM временные файлы удаляются с ведома пользователя.

Доступ S3 и BI отдельно у пользователя не запрашивай: S3 работает тем же ключом с Tenant ID, пароли ClickHouse агент генерирует сам, вход в BI — аккаунтом Cloud.ru. Не отправляй человека искать несуществующую кнопку «получить BI токен».

## Данные и режим

- Разово: один файл → период/смысл показателей → срок доступности ссылки. Спросить «Как долго нужен доступ к отчёту?» Разовый импорт не означает разовый счёт: работающие ресурсы продолжают тарифицироваться.
- Новые файлы вручную: пользователь присылает очередной полный снимок; агент обновляет отчёт.
- Автоматически: конкретный источник + разрешённый доступ + частота + часовой пояс. Реализован один приватный S3-объект `source/sales.csv` в бакете сценария.
- Google Drive/Dropbox/1С/Ozon/WB: сначала проверить наличие коннектора; до реализации предложить разовый файл или обновление по запросу.

Отсутствие новых данных показывать как «новых данных пока нет», сбой доступа — как «не удалось обновить, последний успешный отчёт сохранён».

## Смета и финальная передача

Читайте [стоимость и управление](product.md). До расходов — полная оценка и одно согласие (SKILL.md); после проверки — ссылка, способ входа, период, дата данных, режим обновления и месячная стоимость. Пользователь не получает Terraform state, ключи или технический перечень как основной результат.
