# Первые шаги пользователя

## Первое сообщение после установки

«Помогу получить отчёт по выручке и марже в облаке. Техническую настройку выполню сам. Сначала нужны три ответа:
1. У вас уже есть аккаунт Cloud.ru: да, нет или не уверены?
2. Откуда берём продажи: готовый файл, облачная папка или учётная система?
3. Отчёт нужен один раз или с обновлением? Если пока не решили — начнём с разового.
Ключи и пароли сюда не присылайте. Перед созданием ресурсов покажу стоимость.»

Не спрашивай повторно то, что уже известно. Предложи простой пример выгрузки только после ответа об источнике. Сначала проверь возможность безопасного подключения в данном агенте: skill installation не означает наличие облачного MCP.

## Подробное сопровождение: обязательный маршрут

Для регистрации, выбора проекта, сервисного аккаунта и ключа прочитай [пошаговые карточки первого входа](first-time-cloud.md). Перед шагом ролей прочитай [проверенные названия и области доступа](access-roles.md). Это основной маршрут, а не необязательная справка.

Веди по одному экрану: зачем → куда нажать → точное значение → ожидаемый результат → короткое подтверждение. Если пользователь уже написал «аккаунт есть, тестовые данные», начни с выбранного проекта; не повторяй регистрацию и вопросы. Не выдавай всю инструкцию разом, если пользователь этого не попросил. На этапе ручного действия жди результата; независимую подготовку выполняй сам.

При несовпадении интерфейса спроси название страницы и видимые пункты без секретов. Не выдумывай кнопки, роли и обязательные поля. Не предлагай права администратора организации ради простоты. Права человека на создание аккаунта и права программы на сервисы объясняй отдельно. При нехватке прав подготовь конкретное сообщение администратору.

## Безопасный ввод

Предпочитай встроенный secret store/защищённую форму текущего агента или проверенного оператора MCP. Сообщи пользователю, куда именно передаётся ключ и кто получает доступ. Не называй обычный чат защищённой формой.

Для первичного подключения готов scripts/connect_cloud.py; для уже созданного облачного исполнителя — credentials.py. Агент сам подготавливает команду и доверенный терминал, пользователю остаётся вставить значения в поля без эха. Объяснение: «Во время вставки символы не отображаются — это нормально. Вставьте идентификатор ключа, нажмите Enter, затем секрет и Enter. Значения не попадут в чат». Не читать clipboard или секретные файлы обратно ради проверки. Проверка — успешный read-only API-запрос.

Для первичного bootstrap, когда облачной VM ещё нет, используется защищённое окружение API-клиента агента/оператора, без запуска локального приложения. После создания VM агент переносит доступ в защищённое окружение облачного runtime. Не предлагай ввести ключ на несуществующем сервере. Если доступного безопасного механизма нет, сообщи это до создания ключа и не проси секрет в чат.

Доступ S3 и BI запрашивай только при достижении соответствующего шага. Все генерируемые системой пароли создаёт агент на исполнителе. Нужный вид BI API credentials сначала проверяется: нет подтверждённого универсального обмена Cloud.ru IAM → Superset JWT. Не отправляй человека искать несуществующую кнопку «получить BI токен».

После проверки: «Доступ подключён к проекту [название]. Дальше техническую настройку выполню сам. Сейчас проверю данные и покажу месячную стоимость».

## Данные и режим

- Разово: один файл → период/смысл показателей → срок доступности ссылки. Спросить «Как долго нужен доступ к отчёту?» Разовый импорт не означает разовый счёт: работающий BI продолжает тарифицироваться.
- Новые файлы вручную: пользователь присылает очередной полный снимок; агент обновляет существующий отчёт. Это обновление по запросу, не автоматический сбор.
- Автоматически: конкретный источник + разрешённый доступ + частота + часовой пояс. Сейчас реализован один приватный S3-объект `source/sales.csv` в бакете сценария. Подготовку доступа выполняет агент. Источник должен действительно доставлять туда новые данные.
- Google Drive/Dropbox/1С/Ozon/WB: сначала проверить наличие поддерживаемого коннектора и его права. Не выдавать предложение интеграции за уже работающий коннектор. До реализации предложить разовый файл или обновление по запросу.

Отсутствие новых данных показывать как «новых данных пока нет», сбой доступа — как «не удалось обновить, последний успешный отчёт сохранён». Не объявлять повтор старого файла свежими продажами.

## Смета и финальная передача

Читайте [стоимость и управление](product.md). До расходов — полная оценка и согласие; после проверки — ссылка, способ входа, период, дата данных, режим обновления и месячная стоимость. Пользователь не получает Terraform state, ключи или технический перечень как основной результат.
