# Первый раз в Cloud.ru: маршрут с сопровождением

> **С версии 0.3.0** сервисный аккаунт, его роли и ключ создаёт сам шаблон развёртывания (`service_account_id: null`), а bootstrap ведётся личным ключом доступа пользователя, потому что API Data Platform не принимает сервисные аккаунты (проверено 28.10.2026). Пользователь выполняет только шаги из [console-steps.md](console-steps.md). Разделы ниже про сервисный аккаунт и назначение ролей — справка на случай, если организация запрещает автоматическое создание аккаунтов.

Для агента: выдавай только текущую карточку, а не весь документ. Пользователь может открыть этот файл как полную инструкцию. Сначала прочитай onboarding.md. Маршрут сверён с официальными источниками 28.10.2026; прохождение новичком в реальном кабинете ещё не проверено. Названия ниже — из документации, а не наблюдение текущего экрана пользователя.

## Как объяснять каждый шаг

Каждая карточка содержит: **зачем → где открыть → что нажать/ввести → что должно получиться → какой короткий ответ нужен → что делать при отличии**. В одном сообщении одна небольшая цель, обычно 2–5 действий. Длинную форму разбивай. «Готово» подтверждает только текущую цель. Сохраняй в контексте этап, проект, уже выполненные действия и препятствие, без секретов. Возобновляй с этого места.

Не отправляй человека «назначать необходимые роли», «настраивать IAM», «получать credentials» или «следовать документации» без конкретных действий. Технический термин при первом употреблении объясняй: проект — отдельное рабочее пространство; сервисный аккаунт — отдельный доступ для программы; роль — список разрешённых действий; ключ — секрет для подключения программы. Источник служит проверкой, а не заменой инструкции.

Если кнопки нет, попроси **название страницы и текст видимых пунктов**, без личных данных. Не выдумывай положение кнопки. Не проси скриншот окна ключа. Если пользователь сам прислал безопасный снимок другого экрана, используй его только если клиент умеет читать изображения; браузер агента не нужен. Запрет на браузерную автоматизацию сохраняется.

## А. Начало: выбери только подходящую ветку

**Аккаунта нет:** «Начнём с вашего входа в облако. Откройте [Cloud.ru](https://console.cloud.ru). Найдите “Зарегистрироваться”. Напишите “вижу регистрацию” или название открывшейся страницы». Затем уточни: для личного теста или от имени компании? Не регистрируй компанию автоматически ради теста.

**Аккаунт есть:** «Войдите в [личный кабинет](https://console.cloud.ru) привычным способом. Пароль и коды вводите только на сайте. Когда откроется кабинет, напишите “вошёл”». Далее В.

**Приглашён в компанию:** используй уже выданный организацией способ входа. Не создавай вторую организацию. Если приглашение не принято — попроси завершить его самостоятельно; если нет доступа к проекту — ветка Ж.

## Б. Регистрация

### Б1. Личный тест: телефон и почта

1. На регистрации укажите свой российский номер телефона. Если подходящего номера нет, не обещайте, что этот способ сработает; уточните доступный путь у поддержки Cloud.ru.
2. Введите код из СМС **на сайте**. Ответьте агенту только «телефон подтверждён».
3. На следующем соответствующем экране укажите почту для входа. Найдите письмо с кодом, включая папку «Спам», и введите код на сайте. Ответьте «почта подтверждена».
4. Заполните имя/фамилию и задайте собственный пароль по требованиям формы. Не присылайте пароль агенту.
5. Если сайт снова просит подтверждение телефона, выполните его на сайте. Не начинайте регистрацию заново.

**Результат:** кабинет или следующий экран оформления облака. Напишите название экрана. Агент не называет регистрацию завершённой, пока вы ещё на форме подтверждения.

### Б2. Если удобнее Сбер ID

На странице входа выберите «Войти Сбер ID», подтвердите вход в своём банковском приложении предложенным способом. Если Cloud.ru запросит почту — подтвердите её на сайте. При предложении создать облако сообщите агенту название следующего экрана без персональных данных: он разберёт именно эту форму. Не передавайте агенту QR-код входа или подтверждения.

Источник Б1–Б2: [регистрация](https://cloud.ru/docs/console/ug/topics/guides__registration). Не повторяй механически дублирующийся шаг телефона из статьи и не придумывай кнопку завершения, которой источник не называет.

### Б3. Если нужен договор на компанию или ИП

Это отдельная ветка, не обязательная часть личного теста.

1. На регистрации выберите «Юридическое лицо», затем «Самостоятельно». Если уже вошли как физлицо: инициалы справа сверху → имя профиля → «Организации» → «Зарегистрировать юрлицо».
2. Найдите компанию по названию, ИНН или ОГРН; выберите совпадающую запись. Если записи нет, используйте предусмотренный Cloud.ru путь через менеджера, а не чужую компанию.
3. Переходите по форме по одному экрану. Контакты, способ доставки документов и подтверждающие документы заполняйте непосредственно в Cloud.ru. Агент объясняет текущие поля; состав документов сверяет с веткой «Для компаний» или «Для ИП».
4. После отправки анкеты дождитесь счёта. До оплаты уточните сумму, назначение и условия. Не переводите названную агентом произвольную сумму. Счёт оплачивает пользователь/бухгалтерия.
5. Дождитесь проверки; её состояние смотрите в «Организации». Это не мгновенная регистрация.

**Результат:** регистрация организации завершена и доступна Evolution. Источник: [регистрация юрлица](https://cloud.ru/docs/console/ug/topics/guides__registration_yl).

## В. Выбрать пространство для отчёта

«Проект отделяет ресурсы отчёта от других задач. Найдите список проектов в верхней панели кабинета и раскройте его. Напишите название выбранного проекта и есть ли в нём важные рабочие ресурсы. Номера и ключи пока не нужны».

Для уже согласованного пустого проекта выберите его и подтвердите название. Для нового: в раскрытом списке нажмите «Создать проект», задайте `Отчёт по продажам`, выберите подходящий каталог и нажмите «Создать». Каталог — папка для проектов; если их несколько и назначение непонятно, уточните у владельца организации. Не выбирайте случайный.

**Результат:** проект появился в списке и выбран. Создавать проекты может администратор организации. При отсутствии кнопки — ветка Ж, не выдача агенту прав на организацию. [Источник](https://cloud.ru/docs/administration/ug/topics/guides__projects).

## Г. Создать отдельный доступ для агента

До этого этапа агент должен проверить, что в текущем клиенте доступен безопасный ввод, и прочитать [профиль ролей](access-roles.md). Пользователь не должен создавать ключ, который некуда безопасно передать.

### Г1. Открыть форму

«Теперь создадим доступ для программы. Ваш личный пароль мне не нужен».

1. В левом верхнем углу нажмите меню с девятью точками.
2. Откройте «Пользователи», затем «Сервисные аккаунты».
3. В правом верхнем углу нажмите «Создать аккаунт».

**Результат:** форма с названием, описанием и уровнем. Ответ: «форма открылась». Если раздел или кнопка отсутствуют — Ж. [Навигация](https://cloud.ru/docs/foundation-models/ug/topics/api-ref__authentication); это общий путь кабинета, дальнейшие инструкции по API-ключу Foundation Models к нашему сценарию не относятся.

### Г2. Заполнить форму

1. Название: `sales-report-agent`.
2. Описание: `Развёртывание и обновление отчёта по продажам`.
3. Уровень: «Проект». Проверьте, что это согласованный проект отчёта; если поле проекта появляется на следующем экране, проверьте его там.
4. Нажмите «Продолжить».

**Результат:** шаг назначения ролей. Ответ: «вижу роли». Если выбран другой проект, исправьте выбор до создания: уровень и проект этого аккаунта потом не меняются. [Источник](https://cloud.ru/docs/console_api/ug/topics/guides__service_accounts_create).

### Г3. Назначить роли — по одному сервису

Роли определяет агент по [access-roles.md](access-roles.md), не пользователь. Не подменять их фразой «дайте администратора». Права создающего аккаунт человека и права `sales-report-agent` различаются.

Начни с просьбы назвать видимые блоки формы ролей. Объясни: «Нужны разрешения на конкретные сервисы в проекте отчёта. Общие административные права пока не выбираем». Поле «Роли внутри проекта» не означает список ролей Data Platform. Если оно необязательное, оставь пустым в базовом сервисном профиле. Не выбирай автоматически «Администратор проекта» или «Пользователь проекта».

Для каждой строки основной таблицы ролей выдай отдельную карточку:

«Сейчас разрешим создание базы отчёта.
1. В форме ролей найдите сервис **Managed ClickHouse**. Если сервисы сгруппированы, раскройте соответствующий раздел Evolution.
2. Откройте выбор ролей этого сервиса; если есть поиск, введите `dbaas.clickhouse.admin`.
3. Выберите именно `dbaas.clickhouse.admin`.
Должна появиться выбранная роль рядом с сервисом. Напишите “добавил” или названия пунктов, если такого варианта нет».

Повтори с точными значениями из таблицы, объясняя назначение каждой роли. Для Object Storage выбери указанные четыре роли по очереди; `s3e.admin` не предлагай. Для нового BI нужна область, позволяющая создание инстанса в выбранном проекте; не выбирай чужой существующий инстанс. При отличии формы агент выясняет доступные области и сверяет документацию, а не угадывает текст переключателя.

Если список сервисов отсутствует, не заставляй нажимать несуществующий «Добавить роль». Уточни заголовки формы и доступные действия. Создание аккаунта без ролей не считается подключением. Можно продолжить через «Изменить права» после создания, если кабинет действительно позволяет такой путь; результат всё равно проверяется.

### Г4. Завершить и сверить

Перед нажатием «Создать» агент кратко перечисляет реально выбранные сервисы/роли и проект. Пользователь подтверждает совпадение, затем создаёт аккаунт. Ожидаемый результат — `sales-report-agent` со статусом «Активен». Это ещё **не** проверенный доступ к облаку.

Если аккаунт уже создан: найдите его в «Сервисные аккаунты» → меню с тремя точками в строке → «Изменить права» → исправьте только нужные роли → «Сохранить». Не создавайте дубликат и не удаляйте существующие права без выяснения их назначения. [Источник](https://cloud.ru/docs/console_api/ug/topics/guides__service_accounts_edit-access).

## Д. Создать ключ и передать его без чата

Агент сначала сообщает конкретное подготовленное место скрытого ввода. Если его нет, останавливается **до** создания ключа и объясняет доступный вариант в этом клиенте. Не обещает абстрактную «защищённую форму», которой не существует.

1. В списке сервисных аккаунтов нажмите `sales-report-agent`.
2. Найдите «Учетные данные доступа» и выберите вкладку **«Ключи доступа»**. «API-ключи» — другая вкладка, здесь она не нужна.
3. Нажмите «Создать ключ». В описание впишите `Первый тест отчёта`.
4. Выберите ограниченный срок, согласованный для теста; агент называет дату/срок по доступным вариантам формы. Если варианты не известны, сначала уточняет их. Для регулярного режима отдельно планируется обновление ключей.
5. Нажмите «Создать». Не закрывайте окно с **Key ID** и **Key Secret** до безопасного сохранения: секрет показывается один раз.

[Источник](https://cloud.ru/docs/console_api/ug/topics/guides__service_accounts_key-create).

Дальше агент даёт инструкцию именно для подготовленного механизма. Для пользовательского терминала: «В первом запросе вставьте Key ID и нажмите Enter. Во втором — Key Secret и Enter. Символы не показываются — это ожидаемо. В чат значения не вставляйте». Агент сам готовит зависимости и команду; не просит новичка устанавливать Python или править конфиг. Для первоначального подключения применяется `scripts/connect_cloud.py`; серверный `credentials.py` используется позже на облачном исполнителе.

**Результат:** успешная проверка IAM без создания ресурсов. Агент отдельно проверяет разрешённые чтения по сервисам; IAM success не доказывает полноту ролей. До получения ключа не утверждай, что API уже доступен. Не читай секретный файл в вывод ради проверки.

## Е. Что дальше делает агент

«Подключение проверено. Теперь я подготовлю конфигурацию и полную смету. Пока платные ресурсы не создаю». Не проси пользователя искать сети, образы, технические ID или самостоятельно разворачивать базу. Если нужен ID проекта и его нельзя определить API, дай отдельную карточку: список проектов сверху → три точки у нужного проекта → «Скопировать ID проекта». Это идентификатор, не секретный ключ. [Источник](https://cloud.ru/docs/administration/ug/topics/guides__projects).

Если баланс мешает работе, сначала объясни ожидаемые расходы и условия, затем веди пользователя по актуальной форме оплаты. Не обещай, что бонусов хватит на весь сценарий. Перед созданием инфраструктуры требуется согласованная полная смета.

## Ж. Если что-то не получается

| Что видит пользователь | Следующий ответ агента |
|---|---|
| «Не знаю, где я» | Попросить заголовок страницы и 2–3 видимых пункта; вернуть к ближайшему подтверждённому шагу |
| Нет «Создать проект» | Проверить выбранную организацию; объяснить, что новый проект создаёт её администратор; предложить согласованный существующий проект |
| Нет «Создать аккаунт» / «Изменить права» | Проверить проект и права человека; подготовить текст администратору ниже |
| Нет указанной роли или сервиса | Уточнить точный раздел и видимые варианты, сверить справочник/доступность сервиса; не подменять роль похожим названием |
| Форма требует неожиданное поле | Объяснить только после получения названия/описания поля; не угадывать значение |
| Уже есть аккаунт программы | Проверить название, проект и роли; не создавать второй автоматически |
| Закрыто окно Key Secret | Секрет повторно не виден; подготовить новый ключ, выяснить использование старого перед его отзывом |
| Ключ случайно отправлен в чат | Не цитировать его; предложить отзыв и замену, не использовать как обычный способ подключения |
| Ошибка 401/403 | Агент разбирает срок/тип ключа, проект и конкретный запрещённый запрос; не просит сразу все права |
| «Хочу продолжить позже» | Сообщить завершённый этап и следующий шаг, не сохранять секреты в заметку |

Текст для передачи администратору (подставить реальное название проекта):

> Нужен отдельный сервисный аккаунт `sales-report-agent` уровня «Проект» в проекте «…» для пилота отчёта по продажам. Пожалуйста, создайте его или помогите назначить сервисные роли по приложенному списку агента. Права на организацию и её биллинг программе не нужны. Ключи в переписке не передавайте: для них будет отдельный защищённый ввод. Если для Data Platform нужен отдельный аккаунт кластера, согласуйте его профиль отдельно.

Не отправлять это сообщение самому без указания пользователя. Недоступный шаг пользователя не блокирует независимую подготовку файлов и сметы агентом, но не разрешает обход прав.
