# Отчёт по продажам через облачный MCP

Результат: полный CSV-снимок в приватном Object Storage, проверенная витрина Managed ClickHouse и отчёт Managed BI с выручкой и contribution-маржей по каналам. Managed BI относится к Data Platform, Managed ClickHouse — отдельный сервис БД.

Навык не привязан к агенту или ОС. Найди пакет по runtime_root в installation.json рядом с SKILL.md; в исходном репозитории пакет находится на два уровня выше папки навыка. Если установлен только SKILL.md, получи полный пакет из того же доверенного релиза. Не используй пути автора и не придумывай доступные tools.

## Первый контакт

Сразу после установки прочитай [первые шаги](references/onboarding.md) и продолжи разговор: аккаунт есть/нет, источник данных, разовый или обновляемый отчёт. Не заканчивай только сообщением об установке. Пользователь выполняет регистрацию, подтверждения, оплату и первичное предоставление доступа; всю техническую настройку делает агент. Инструкции пользователю выдавай небольшими шагами, без Terraform, UUID, сетей и команд установки.

Проверь поддержку skill, удалённого MCP и безопасного ввода в текущем агенте. Не обещай совместимость с непроверенным клиентом. Заранее размещённого общего MCP в этой поставке нет: по умолчанию отдельный облачный исполнитель клиента. Реализация single-tenant; не смешивать разных клиентов в одном процессе/state/token. Shared endpoint допустим только от проверенного оператора с отдельной изоляцией.

До технического выполнения прочитай [контракт](references/contract.md), [облачный запуск](references/runtime.md) и [стоимость и управление](references/product.md).

## Только MCP и API

Пользователь явно исключил браузер и локальный пилот. Не открывай консоль, не извлекай browser session, не подменяй API действиями UI. Не запускай локальные БД, Docker или демо-сервер. Runtime MCP, данные и worker размещаются в облаке; работа с файлами и API-клиентом агента допустима для первоначальной установки.

Cloud.ru credentials и MCP bearer token — разные секреты. Агенту нужен только доступ к MCP; Cloud.ru ключи хранятся на сервере. При первом запуске помоги пользователю ввести их через защищённый интерактивный терминал, без эха и передачи в чат. Пока пользователь отложил ввод ключей, выполняй разработку, не создавай платные ресурсы.

Для первого облачного MCP требуется однократный bootstrap: агент создаёт ресурсы через тот же фиксированный Terraform API-шаблон, размещает пакет на созданной VM и подключает HTTPS MCP. Сервер не может создать собственный первый хост до своего появления. После bootstrap весь сценарий выполняется MCP tools. Не называй bootstrap через Terraform end-to-end вызовом MCP.

## Развёртывание

1. `sales_configuration` показывает доступность конфигурации, но не подтверждает облако. `cloudru_deployment_catalog` читает зоны, версии ClickHouse и BI flavors через официальный провайдер; получи результат через `cloudru_deployment_status(job_id)`. Остальные технические ID находи разрешёнными API/data sources при подготовке server-side deployment.json.
2. Агент готовит серверный deployment.json: отдельная сеть и подсети, DNS, приватный bucket, один ClickHouse, Data Platform/BI, VM MCP. Используй фактические ID, свободный CIDR, проверенные образы и минимальные спецификации. Не выбирай free tier только по имени; проверь eligibility. Не изменяй чужие ресурсы. Сервисный аккаунт и лог-группа входят в prerequisites и должны быть проверены через API.
3. `cloudru_deployment_plan` → `cloudru_deployment_status`: подготовь действия и полную смету. Агент заполняет проверенные тарифы; `sales_estimate_cost` считает весь сценарий. При total=null нельзя называть частичную сумму полной ценой. Пользователю покажи месячную стоимость, объём и частоту, а не технический bill of materials. Разовый режим включает согласованный срок доступности BI. Только create/no-op допускаются сервером; update/delete/replacement требуют отдельной работы оператора.
4. После согласования расходов оператор разрешает точный hash в защищённом approval.json и включает запись. `cloudru_deployment_apply(plan_sha256)` возвращает job_id; проверяй статус. При неизвестном исходе не повторяй apply и не удаляй intent-файл автоматически. Восстанови фактическое состояние API и Terraform.
5. После успешного создания агент размещает MCP на VM, переносит защищённый state/manifest и настраивает TLS, CA и доступ клиента. `cloudru_use_deployed_resources` привязывает процесс к manifest. Перезапуск требует повторной привязки или сохранённой runtime-конфигурации. Проверь доступность ClickHouse из VM, BI из VM и ClickHouse из BI. Не выключай TLS verification.

## Данные

Согласуй смысл возвратов, НДС и период полного снимка. Для первого технического теста используй синтетический examples/sales-demo.csv; не выдавай его за данные бизнеса.

`sales_stage_csv(csv_text)` сохраняет разрешённые данные на облачном сервере, возвращает filename/hash/суммы. Не передавай персональные данные покупателей. Затем:

1. `sales_preview_csv(filename)` — сверить суммы и полный период.
2. `sales_upload_csv(filename, expected_snapshot_id)` — приватный S3.
3. `sales_prepare_schema()` — таблицы и витрина.
4. `sales_import_snapshot(snapshot_id)` — импорт и сверка до публикации manifest.
5. `sales_report(snapshot_id, group_by)` — суммы; повтор того же импорта не должен менять итоги.

Контрольный файл: 3 строки, выручка 1300, себестоимость 780, комиссии 200, contribution 320, маржа 24,62%. Snapshot заменяет активную витрину, разные снимки не суммируются.

## BI через REST

`sales_bi_probe` проверяет поддерживаемую API-авторизацию инстанса. IAM токен Cloud.ru не считается JWT Apache Superset. Совместимость Managed BI с upstream REST ещё требует реального теста. Если API-доступ не поддерживается, зафиксируй блокирующую операцию и требуемый способ авторизации; браузерный fallback запрещён.

`sales_bi_connect` создаёт соединение из серверного TLS URI отдельного reader. `sales_bi_publish` создаёт dataset витрины, таблицу выручки/contribution по каналам и dashboard. На частичной ошибке сохрани ID, не повторяй POST вслепую. `sales_bi_verify(snapshot_id)` сверяет ID снимка, число строк, выручку и contribution через BI chart-data API с ClickHouse. Это проверка данных, не визуальная приёмка расположения виджетов.

## Обновление и сдача

Предложи разовый файл, новые файлы по запросу или автоматическое получение из поддерживаемого источника. Сейчас реализован приватный S3 source/ объект: `sales_refresh_source` и worker `cloudru_mcp.refresh --source` по облачному timer. Это не готовая интеграция с 1С/Ozon/WB/Google Drive. Настрой источник и расписание до обещания автоматического обновления; проверь scheduled run с новым SHA отдельно. Конфигурация worker должна содержать созданные адреса/ID и защищённые ключи. Остановка таймера не останавливает оплату ресурсов.

В техническом журнале сохраняй стадии: INFRA_APPLIED, CLOUD_DATA_VERIFIED, BI_DATA_VERIFIED, SCHEDULE_VERIFIED. Пользователю — ссылка на человекочитаемый отчёт, способ входа, период/дата данных, режим обновления и месячная стоимость с условиями. Не выдавай успешный plan, опубликованный dashboard или unit tests за облачный e2e. Незавершённый bootstrap, API-доступ к BI или получение входного файла должны быть названы явно. Порядок управления и формат сдачи — в product.md.
