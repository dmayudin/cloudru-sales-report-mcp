# Отчёт по продажам через облачный MCP

Результат: полный CSV-снимок в приватном Object Storage, проверенная витрина Managed ClickHouse и отчёт Managed BI с выручкой и contribution-маржей по каналам. Managed BI относится к Data Platform, Managed ClickHouse — отдельный сервис БД.

Навык не привязан к агенту или ОС. Найди пакет по runtime_root в installation.json рядом с SKILL.md; в исходном репозитории пакет находится на два уровня выше папки навыка. Если установлен только SKILL.md, получи полный пакет из того же доверенного релиза. Не используй пути автора и не придумывай доступные tools.

## Что делает пользователь, а что агент

Пользователь руками выполняет ровно три вещи, каждая описана дословно со скриншотами в [шагах в консоли](references/console-steps.md): входит в консоль и создаёт **личный ключ доступа** (шаг B), копирует **Tenant ID** Object Storage (шаг C), в конце открывает ссылку на отчёт и входит через «Sign in with cloud» (шаг E). Плюс оплата и подтверждения своего аккаунта. Всё остальное делает агент через API: сервисный аккаунт и его роли, сеть, DNS, бакет, ClickHouse, Data Platform, BI, виртуальная машина, установка MCP, сертификат, подключение клиента. Не отправляй пользователя создавать сервисные аккаунты, назначать роли, искать сети, образы и спецификации: шаблон создаёт сервисный аккаунт сам (`service_account_id: null`), а ключ сервисного аккаунта всё равно не работает с API Data Platform.

Инструкции пользователю выдавай по одному шагу, без Terraform, UUID, сетей и команд. Если экран в консоли выглядит иначе, чем в описании, попроси описать, что видно, и сверься с документацией Cloud.ru; не управляй браузером пользователя.

## Первый контакт

Сразу после установки прочитай [первые шаги](references/onboarding.md) и продолжи разговор: аккаунт есть/нет, источник данных, разовый или обновляемый отчёт. Для пользователя без аккаунта используй [карточки первого входа](references/first-time-cloud.md) до момента входа в консоль, затем переходи к console-steps.md. [Профиль ролей](references/access-roles.md) нужен только как справка: роли назначает шаблон. Не заканчивай только сообщением об установке. Проверь поддержку skill, удалённого MCP и защищённого терминального ввода в текущем агенте; не обещай совместимость с непроверенным клиентом. Реализация single-tenant: не смешивать разных клиентов в одном процессе/state/token.

До технического выполнения прочитай [контракт данных](references/contract.md), [порядок bootstrap](references/bootstrap.md), [облачный runtime](references/runtime.md), [стоимость и управление](references/product.md) и [известные проблемы](references/troubleshooting.md).

## Только MCP и API

Пользователь явно исключил браузер и локальный пилот. Не открывай консоль, не извлекай browser session, не подменяй API действиями UI. Не запускай локальные БД, Docker или демо-сервер. Runtime MCP, данные и worker размещаются в облаке; файлы и API-клиент агента допустимы для первоначальной установки.

Cloud.ru credentials и MCP bearer token — разные секреты. Ключ пользователь вводит один раз через защищённый терминал (`scripts/connect_cloud.py`, без эха, без чата); Cloud.ru ключи затем живут только на сервере. Пока пользователь отложил ввод ключа, выполняй подготовку, не создавай платные ресурсы.

Первый облачный MCP требует однократного bootstrap: агент создаёт ресурсы фиксированным Terraform API-шаблоном, размещает пакет на созданной VM и подключает HTTPS MCP. Сервер не может создать свой первый хост до своего появления. После bootstrap весь сценарий выполняется MCP tools. Не называй bootstrap end-to-end вызовом MCP.

## Одно согласие вместо многих

Агентские среды блокируют отдельные действия (платный ресурс по новой цене, правило 0.0.0.0/0, удаление, замена), пока пользователь не разрешил именно их. Поэтому перед apply покажи одну смету и один список и получи одно «да», которое явно покрывает:

1. создание перечисленных ресурсов в пределах сметы (сутки / 7 дней / 30 дней с НДС) и согласованный срок хранения;
2. правило 80/tcp с любых адресов только для выпуска сертификата Let's Encrypt (Caddy отвечает там только на проверку и редирект);
3. запасной вариант: платный флейвор Managed BI с ценой, если бесплатный не создаётся;
4. право один раз отвязать и пересоздать сбойный ресурс по инструкции troubleshooting.md; удаление зависшего кластера всё равно делает поддержка.

Формулировка пользователю: «Создаю всё перечисленное на сумму до X ₽ за N дней, открываю порт 80 для сертификата, при сбое бесплатного BI беру платный за 3,79 ₽/час, сбойный ресурс пересоздаю один раз. Подтверждаете?». Всё, что выходит за это согласие (второе пересоздание, другой флейвор ClickHouse, удаление данных), спрашивай отдельно с ценой.

## Развёртывание

1. `sales_configuration` показывает доступность конфигурации, но не подтверждает облако. До появления MCP discovery делается провайдером из API-клиента агента (bootstrap.md, раздел 2); после — `cloudru_deployment_catalog` → `cloudru_deployment_status(job_id)`.
2. Серверный deployment.json: отдельная сеть и две подсети, DNS-сервер, приватный bucket, один ClickHouse, Data Platform/BI с внешним адресом, VM MCP, сервисный аккаунт (создаётся шаблоном). Используй фактические ID, свободный CIDR, проверенные образы и минимальные спецификации. Free tier BI проверяй по факту (один на организацию), не по названию.
3. `cloudru_deployment_plan` → `cloudru_deployment_status`: действия и полная смета (`sales_estimate_cost`). При total=null нельзя называть частичную сумму полной ценой. Только create/no-op допускаются сервером; update/delete/replacement — отдельная работа оператора с согласия.
4. После единого согласия оператор пишет approval.json и включает запись. `cloudru_deployment_apply(plan_sha256)` → job_id → статус. При неизвестном исходе не повторяй apply; восстанови фактическое состояние API и Terraform.
5. Ожидание: ClickHouse обычно 15–40 минут; если хостов нет через 45 минут и операция создания не обновляется — это известный сбой платформы, не конфигурации (troubleshooting.md). Не создавай новые кластеры «на пробу» без отдельного согласия: их нельзя удалить до вмешательства поддержки.
6. После создания агент размещает MCP на VM, переносит единственный Terraform state и manifest, настраивает TLS (порт 80 для ACME), CA и доступ клиента. `cloudru_use_deployed_resources` привязывает процесс к manifest. Проверь ClickHouse из VM, BI из VM и ClickHouse из BI. Не выключай TLS verification.

## Данные

Согласуй смысл возвратов, НДС и период полного снимка. Для первого технического теста используй синтетический examples/sales-demo.csv; не выдавай его за данные бизнеса.

`sales_stage_csv(csv_text)` сохраняет разрешённые данные на облачном сервере, возвращает filename/hash/суммы. Не передавай персональные данные покупателей. Затем:

1. `sales_preview_csv(filename)` — сверить суммы и полный период.
2. `sales_upload_csv(filename, expected_snapshot_id)` — приватный S3.
3. `sales_prepare_schema()` — таблицы и витрина.
4. `sales_import_snapshot(snapshot_id)` — импорт и сверка до публикации manifest.
5. `sales_report(snapshot_id, group_by)` — суммы; повтор того же импорта не должен менять итоги.

Контрольный файл: 3 строки, выручка 1300, себестоимость 780, комиссии 200, contribution 320, маржа 24,62%. Snapshot заменяет активную витрину, разные снимки не суммируются.

## BI через REST

`sales_bi_probe` проверяет поддерживаемую API-авторизацию инстанса. IAM токен Cloud.ru не считается JWT Apache Superset. Если API-доступ не поддерживается, зафиксируй блокирующую операцию и предложи пользователю собрать дашборд в интерфейсе BI по готовой витрине (вход «Sign in with cloud»); браузерный fallback агента запрещён.

`sales_bi_connect` создаёт соединение из серверного TLS URI отдельного reader. `sales_bi_publish` создаёт dataset витрины, таблицу выручки/contribution по каналам и dashboard. На частичной ошибке сохрани ID, не повторяй POST вслепую. `sales_bi_verify(snapshot_id)` сверяет ID снимка, число строк, выручку и contribution через BI chart-data API с ClickHouse.

## Обновление и сдача

Предложи разовый файл, новые файлы по запросу или автоматическое получение из поддерживаемого источника. Реализован приватный S3 source/ объект: `sales_refresh_source` и worker `cloudru_mcp.refresh --source` по облачному timer. Это не интеграция с 1С/Ozon/WB/Google Drive. Остановка таймера не останавливает оплату ресурсов. Срок MCP-токена ограничен: продление делает агент (`rotate_token.py` на VM), пользователя это не касается.

В техническом журнале сохраняй стадии: INFRA_APPLIED, CLOUD_DATA_VERIFIED, BI_DATA_VERIFIED, SCHEDULE_VERIFIED, плюс ID ресурсов, обращения в поддержку и их статус. Пользователю — ссылка на отчёт, способ входа, период/дата данных, режим обновления и месячная стоимость с условиями. Не выдавай успешный plan, опубликованный dashboard или unit tests за облачный e2e. Незавершённый bootstrap, зависший кластер, API-доступ к BI или получение входного файла называй явно. Порядок управления и формат сдачи — в product.md.
