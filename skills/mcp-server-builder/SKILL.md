# Разработка MCP-сервера

Сначала определи пользовательский результат, целевой MCP-клиент, доступные API и границу полномочий. Не считай реализацию протокола доказательством работоспособности внешней интеграции.

## Исследование и контракт

- Прочитай существующий сценарий и его данные. Выдели необходимые операции чтения и изменения; не экспортируй весь REST API автоматически.
- Проверь методы, пути, авторизацию, схемы, пагинацию и ограничения по первичным источникам. Сохрани ссылки и дату проверки в документации реализации. Не придумывай endpoint или поля API; явно выдели неизвестное.
- Выбери официальный SDK, зафиксируй зависимости и совместимую версию протокола. Сверяй примеры с установленной версией SDK: старые и новые редакции MCP могут различаться.
- Используй stdio для локального запуска или Streamable HTTP для удалённого сервиса. При stdio stdout содержит только протокол; диагностика идёт в stderr.

## Инструменты

- Назови инструменты по действиям предметной области. В описании укажи назначение, ограничения, источник идентификаторов и побочные эффекты.
- Задай строгие входные схемы, ограничения размеров, enum и обязательные поля. Для структурированных результатов используй выходную схему. Проверяй значения на сервере.
- Возвращай компактный результат, идентификаторы и следующий допустимый шаг. Большие выборки ограничивай и разбивай на страницы.
- Ошибки выполнения возвращай как ошибки инструмента с полезным сообщением; ошибки структуры протокола оставь SDK. Не раскрывай токены, пароли, исходные тела ошибочных ответов и stack trace.
- Помечай операции чтения и изменения корректными аннотациями SDK; аннотации не заменяют проверку прав.

## Внешние операции

- Раздели протокольный слой, бизнес-логику и адаптер внешнего сервиса. Позволь подменять адаптер в тестах.
- Ограничь ресурсы конфигурацией оператора; не принимай произвольные URL, SQL или shell-команды, если сценарий этого не требует. Проверь доступ к каждому объекту, включая запрос по ID.
- Секреты читай из окружения или secret store. Для HTTP проверяй аутентификацию, назначение токена и права; stdio запускай с минимальными правами. Не считай переданный пользователем ID доказательством доступа.
- Для изменений предусмотрь идемпотентность или явную проверку исхода перед повтором. Не повторяй неидемпотентный запрос после сетевой ошибки вслепую. Для долгих операций используй ID и проверку статуса.
- Задай таймауты, лимиты и ограниченную обработку временных ошибок. Отделяй неподтверждённый результат от успеха. Одобрение разработки не разрешает платное развёртывание.

## Проверки и передача

- Проверь реальные MCP list/call через SDK client или Inspector, а не только прямые Python/JS функции.
- Проверь контрольный бизнес-кейс, неверные аргументы, отсутствие доступа, пагинацию, сбой провайдера, повтор изменения и отсутствие секретов в ошибках.
- Используй синтетические данные для локальных проверок. Отдельно обозначь mocked integration, локальный protocol test и live test; не подменяй одно другим.
- Подготовь команду установки и запуска, пример конфигурации клиента без секретов, список переменных окружения и следующий пользовательский тест. Не обещай уже установленное подключение без проверки.
- При наличии агента для eval оцени выбор инструментов и успешность сценария; иначе предоставь воспроизводимые пользовательские задания и честно обозначь, что agent eval не выполнялся.
